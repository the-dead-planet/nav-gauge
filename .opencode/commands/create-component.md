Create this UI component: $ARGUMENTS

Load and follow the `add-ui-component` skill. Design the implementation as a coherent whole, rather than accumulating local patches.

1. Search for existing components, hooks, value helpers, and theme sizing before adding code. Reuse or compose them; remove contradictory selectors, cascade-dependent behavior, duplicated state machines, dead definitions, obsolete compatibility code, and accidental abstractions in code you replace.
2. Read `ui/web/src/design-system/Overview.mdx` and the relevant linked foundations once. Use `Appearance.mdx` for variants, defaults, and states; `Theming.mdx` and `colors/Colors.mdx` for palette and elevation behavior; `Sizing.mdx` for geometry. Reuse already-loaded guidance.
3. State which existing UI layer owns the component and why, following `.opencode/rules/architecture.mdc`. Choose the lowest layer owning its semantics. If a genuinely distinct reusable responsibility needs a new layer, explain it and update the architecture rule, Draw.io source, and generated SVG.
4. Locate the common API, both renderers, stories, and relevant tests. Use Button as the default reference on each platform; consult Checkbox, NumberInput or Dropdown only for form-field patterns. Open another reference only when these do not cover the needed pattern, and state why. For callers, grep usage; read implementations only if the public API or shared behavior changes. Update every affected caller when changing an API.
5. Put the shared public API, genuine design policy, and platform-neutral value logic in `ui/common`, with thin web and mobile renderers and the existing barrel exports. Keep platform-only props local. Reuse shared types, appearance defaults, and `theme.sizes` / `--size-*` tokens instead of component-specific size tables when the geometry has the same purpose.
6. Check every supported variant against the appearance tables: default, hover/focus, pressed/persistent highlighted, and disabled. Disabled wins; pressed/highlighted wins over hover/focus; interactive states use `highlightColor ?? color`. Preserve a visible focus indicator while highlighted and keep form labels independent of transient field interaction.
7. Use the common appearance model as the source of truth. Web consumes generated `--appearance-*` variables directly; mobile uses `Theme.color()` and `Theme.resolveAppearance()`. Support every palette and status `ColorVariant` without component-local color/variant/mode matrices, aliases, or status special cases. Scope arbitrary runtime shade overrides to shared appearance override variables resolved against the selected base/highlight color.
8. Use shared elevation policies: `raised` for persistent panels/toolbars, `floating` for transient widgets, and `overlay` for popups/menus/dialogs. Select direction in the renderer. Globally stacked surfaces consume the combined layer policy; do not choose z-index and elevation independently or assemble custom drop shadows.
9. Give interaction state one owner. Composed visual primitives render geometry without reconstructing the parent's state machine. Keep web selectors/SVG and mobile `StyleSheet`/native interaction platform-specific. Preserve semantics, keyboard focus, accessibility, and disabled behavior.
10. Follow the skill's story requirements. Playground and Gallery must both support direct interaction and drawer controls, synchronized through the same story args; one shared Gallery value is fine. Use web `useArgs()` decorators and the mobile renderer's `updateArgs` argument instead of private per-cell state. Compose shared gallery primitives for supported variant, palette/status color, size, and shape dimensions; show one selected size. Expose only controls the Gallery does not fix. Do not force palette rows onto arbitrary-value controls without a palette appearance API. Delete redundant disabled, size, shape, and interaction stories.
11. Test new behavior and regressions proportionally. Shared theme tests own exhaustive policy combinations; component tests cover representative rendering/state ownership and interaction rather than repeating the full color × variant × mode × size matrix. Prefer extending an existing focused test to adding another suite.

Review the complete affected state system once after editing. Run affected `yarn typecheck:web` and `yarn typecheck:mobile:once`, focused tests, `yarn lint`, and `git diff --check`; check browser/device behavior when relevant. Report tooling failures separately from code failures. Keep the implementation minimal and stop after the task and checks are complete.
