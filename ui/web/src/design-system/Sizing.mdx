# Sizing

The shared component size scale is `xs`, `sm`, `md`, and `lg`. Components that expose `size` must support the complete scale on both platforms. The standard default is `sm` unless a component documents a reason to use another size.

These values come directly from the shared control size policy used by both platforms. Controls and their accompanying surfaces use its font, icon, gap, and padding metrics directly. Distinct shape geometry may derive measurements from this scale in the common component package; do not introduce separate component size tables in the theme. `size` must not add external margin or layout spacing around arbitrary child content.

Track-based controls, including sliders and color ramps, share `thumbSize`: the square side length before rotation; diamond thumbs rotate that square 45°. Standard Slider tracks use `trackThickness`, while hue and opacity ramp tracks use half the shared control `height`. Diamond endpoint caps use a side length of `trackThickness / √2`, so their diagonal matches the standard track thickness.

## Layout Boundary

- Callers own external margin, positioning, and composition spacing.
- Containers do not impose content padding unless padding is part of their documented contract.
- Surface geometry and appearance do not imply content padding.
- Full-width content such as selectable rows may extend to a shaped container's clipped edge.

Use spacing tokens for layout spacing. Do not overload component `size` as a general-purpose padding prop.

On web, put `data-size={size}` on the control or its container; `HudSurface` emits it from its `size` prop. `useThemeVariables` maps that size to inherited `--size-control-*` metrics. Consume those variables directly instead of repeating geometry rules for each size. Set the size again at nested controls and portal roots that select their own size. Mobile renderers read the same metrics from `theme.sizes.control[size]`.

Document component-specific sizing contracts in the component's own documentation.
